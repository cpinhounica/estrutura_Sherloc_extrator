Antes de começar

Termos usados neste documento

Explicação em português simples dos termos técnicos que aparecem nas próximas abas. Não precisa decorar — é só para consultar sempre que aparecer uma palavra estranha.

Como o sistema é organizado

Tenant (inquilino / cliente)

Cada seguradora que usa o sistema. Um único programa atende várias, mas cada uma só enxerga os próprios dados.

Multi-tenant

Quando um mesmo sistema atende vários clientes ao mesmo tempo, cada um isolado dos outros — em vez de um sistema separado para cada cliente.

Deploy

O ato de publicar uma versão do sistema rodando de verdade, disponível para uso.

Pipeline

A sequência de passos que um dado percorre até virar resultado. Ex.: documento → leitura → extração → validação → salvar.

Motor de regras

A parte do sistema que decide o que é ou não coberto pelo seguro, de forma configurável — sem precisar reescrever código para cada regra nova.

Configurador

A peça que permite ajustar o comportamento do sistema (regras, documentos exigidos) preenchendo dados, em vez de programar de novo.

Onde os dados ficam guardados

MongoDB / Mongo

O banco de dados onde ficam guardadas as informações do sistema (cadastros, regras, resultados).

Coleção (collection)

Dentro do Mongo, equivale a uma "tabela": um grupo de registros do mesmo tipo. Ex.: a coleção Tenants guarda um registro por seguradora.

S3 / bucket

O serviço da Amazon onde ficam guardados os arquivos (PDFs, fotos de documentos). Um "bucket" é como uma pasta grande nesse serviço.

Secrets Manager

Um cofre digital da Amazon onde ficam senhas e chaves de acesso, em vez de deixá-las escritas no meio do código.

Cache / TTL

Cache é uma "memória rápida" que guarda um resultado já calculado para não repetir o trabalho. TTL é por quanto tempo essa informação continua valendo antes de precisar buscar de novo.

Acesso e segurança

API

A "porta de entrada" pela qual outros sistemas conversam com o Sherlock ou o Extrator para pedir alguma coisa.

Endpoint

Um endereço específico dentro da API que faz uma única coisa. Ex.: o endereço que recebe um documento para extrair dados dele.

Credencial

O "usuário e senha" (ou equivalente) que identifica quem está fazendo um pedido ao sistema.

Hash

Uma versão embaralhada e sem volta de uma senha, guardada no banco no lugar da senha real — assim, mesmo se alguém acessar o banco, não descobre a senha.

Inteligência artificial

LLM

O modelo de inteligência artificial (como o Claude ou o GPT) que lê e interpreta o texto dos documentos e sinistros.

RAG

Técnica em que a IA primeiro busca o trecho certo dentro de um documento (ex.: as condições gerais da apólice) e só depois responde com base nele — isso evita que ela "invente" uma resposta.

Código e processamento

Repositório (repo)

A pasta com todo o código-fonte de um projeto, com histórico de todas as alterações já feitas.

Branch

Uma cópia paralela do código, usada para testar ou desenvolver algo sem mexer na versão principal.

Schema

A "receita" que descreve quais campos um documento ou dado deve ter, e de que tipo (texto, número, data...).

Fila (SQS)

Uma lista de tarefas pendentes que vão sendo processadas uma de cada vez, em vez de todas juntas — evita sobrecarregar o sistema.

Princípio do configurador

O motor de execução (autenticação, resolução de tenant, motor de regras, RAG, fila) é código, escrito uma vez. O que muda de cliente para cliente e de ramo para ramo é dado: linhas em coleções do Mongo. Trocar de seguradora ou adicionar um ramo novo deve significar inserir documentos, não abrir um editor de código. Isso só é verdade hoje para uma fatia do Extrator (templates genéricos) — no Sherlock, é o oposto: tudo é código fixo para vida.

⚠ Lacuna identificada

O desenho previa "Sherlock chama o Extrator com a credencial do próprio tenant" — mas CredenciaisAPI guarda segredo_hash (hash, irreversível). Não dá para reapresentar a senha do cliente numa chamada de saída. Por isso o campo service_auth acima: uma credencial de serviço, separada da credencial que o cliente usa para chamar a API, só para tráfego Sherlock→Extrator.

Resolução por requisição

Componente novo, replicado nos dois repositórios (avaliar extrair como lib compartilhada): app/config/tenant.py com TenantConfig (Pydantic), TenantResolver (carrega + cacheia com TTL) e a dependency CurrentTenant. No Extrator, ele substitui o singleton settings.db; no Sherlock, ele cria a primeira conexão Mongo que o serviço já vai ter.

Documentos exigidos — reaproveitar o que o Extrator já tem

O Extrator já separa tipos de documento "de sistema" (CNH, RG, certidão de óbito — com prompt dedicado) de tipos "genéricos" (schema livre, criado por exemplo). Para ramos novos, a maioria dos documentos exigidos (BO, apólice, laudo pericial) pode simplesmente entrar pelo caminho genérico já pronto — só documentos que precisam de um prompt especial e feito à mão (como a certidão de óbito hoje) exigem trabalho de engenharia. Isso é herdado direto de tenant.seguros[ramo].documentos_exigidos, campo que já apontava para IDs do Extrator no desenho original — só faltava o motor de regras do outro lado para dar uso a ele.

Pré-requisito antes de construir o motor

Consolidar os três pipelines do Sherlock (aba Diagnóstico) e unificar as entidades duplicadas primeiro. Construir o configurador em cima de dois modelos de dados paralelos multiplica o trabalho por dois — e um dos três pipelines já está morto em produção, então essa limpeza reduz código antes de adicionar código novo.
